Reviewer model: `opencode-go/kimi-k3.1-pro#high` (development/review assistant only)
Method: static inspection of `docs/PROJECT_BRIEF.md`, `AGENTS.md`, README,

## What we are building and the safety model (10 lines)

1. AnyBridge is a local-first MCP server for operating CLI and browser software without ready-made integrations.
2. Discovery exposes observed capabilities as numbered menu items rather than asking the model to generate commands, selectors, or URLs.
3. The model compiles an intent into a typed workflow containing steps and independent outcome checks.
4. Execution is intended to be deterministic, permissioned, and separate from model-driven discovery and planning.
5. CLI executables, browser origins, filesystem paths, step counts, and destructive effects are deny-by-default policy concerns.
6. Discovery of a capability does not itself grant permission to exercise that capability.
7. A human must approve the exact plan out-of-band using a single-use, hash-bound, expiring approval; the model must not be able to approve.
8. Policy must be checked again against the fully resolved execution step, including substituted replay parameters.
9. Only engine-computed verification evidence may establish success, and only verified workflows may be saved.
10. Saved workflows must be hash-pinned and versioned so model-free replay cannot silently execute edited or drifted behavior.

## Contradictions and gaps between brief and code

| Brief / documented expectation | Current implementation |
| --- | --- |
| Model uses only menu IDs and never writes code, selectors, or URLs. | `proposeWorkflow` accepts arbitrary `cli.*`, `browser.*`, `fs.*`, and `assert.*` actions (`src/workflow/index.ts:77-84`); the tool schema permits arbitrary argv, URLs, and locators (`src/server.ts:51-69`). |
| Approval uses `anybridge approve <plan_id>` in a separate terminal. | No approval module or approve command exists; `src/index.ts:1-7` only starts the MCP server. The model receives and returns the hash. |
| Approval is single-use, hash-bound, and expiring. | No expiry or approval record; `executed` is not checked before re-execution (`src/workflow/index.ts:9-19,121-147`). The hash omits most step content. |
| Policy is rechecked on the resolved execution step. | Proposal effect checks are not repeated in `executeWorkflow`; replay has no proposal-level validation (`src/workflow/index.ts:121-147,218-241`). |
| Browser origin allowlist applies to every request. | Inspection ignores a failed allowlist check (`src/discovery/index.ts:66-80`); execution checks only initial `browser.goto`, not redirects, subresources, or later navigation. |
| CLI allowlist contains absolute `.exe` paths. | Defaults contain bare names such as `node`, `npm`, and `npx` (`src/policy/allowlist.ts:11-17`). |
| Path jail uses realpath checks. | `isPathInJail` performs lexical resolve/prefix checks (`src/policy/allowlist.ts:40-45`); CLI path checking is skipped (`src/execution/executor.ts:33`). |
| Verification independently proves outcome. | Verification mostly inspects prior audit JSON and does not independently read DOM/filesystem or establish hash baselines (`src/workflow/index.ts:157-195`). |
| Saved workflows are hash-pinned and versioned. | Store reads/writes mutable `<name>.json` with no stored hash/integrity check and overwrites names (`src/workflow/store.ts:27-41`). |

| Secrets are referenced as `{{secret:NAME}}`. | Placeholders remain unresolved (`src/workflow/index.ts:25-32`); browser fill values enter audit observations (`src/execution/executor.ts:117-123`). |
| Additional documented behavior | `follow` is not implemented for browser inspection, `maxToolCallsPerTask` is not server-enforced, unknown verification kinds are accepted, and replay parameter types are not validated. |

## Existing test coverage gap

The current 11 tests cover basic help/ARIA parsing, simple allowlist membership,
lexical path prefixes, and store save/load round-tripping. They do not cover:

- Approval origin, consumption, expiry, or plan-content binding.
- Execution/replay resolved policy enforcement.
- Redirects, subresources, disallowed inspection, or cross-plan browser state.
- Windows junctions, executable identity, `.cmd` behavior, or process-tree timeout.
- Independent verification, unsupported checks, stale verification, or replay verification.
- Store traversal, tamper detection, version pinning, or menu-ID rebinding.
